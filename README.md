# Anomaly Detection Toolkit

![tests](https://github.com/Jazzye2/anomaly-detection-toolkit/actions/workflows/tests.yml/badge.svg)

**Live app:** https://anomaly-detection-toolkit.streamlit.app/

Want to deploy your own copy on AWS instead? See [DEPLOY_AWS.md](DEPLOY_AWS.md).

Thinking about scaling this to real, large data? See [poc/](poc/) for an
Athena-based scoring approach, verified to match the Python logic exactly,
and the specific real public dataset it's designed for.

A reusable peer-group anomaly detection pipeline: score a numeric column
against a leave-one-out peer cohort, train a tuned Random Forest on the
flags, and explain any individual prediction with SHAP.

Built out of the methodology developed for WGU D797 JCN1 Task 1
(hospital staffing anomaly detection, as a stand-in for Medicare
fraud/abuse-style outlier analytics). The math and the model choice are
validated against that dataset; the code itself is not tied to it,
point it at any tabular dataset with a numeric column worth screening
and categorical columns that define a sensible peer group.

**What this is not:** a production-ready Medicare fraud detector. It does
run against real, public CMS billing data (see the POC results below and
in `poc/`), but as a demonstration against historical public data, not a
live connection to claims processing or any protected/restricted CMS
system, and it shouldn't be pointed at real claims or beneficiary data
outside CMS's own authorized systems. This is the methodology, validated
on real data and portable to a new dataset, not a finished product.

## Why leave-one-out, not a plain z-score

A plain z-score computes a cohort's mean and standard deviation using
every row in the cohort, including the row being scored. In a small
cohort, one genuine outlier inflates that cohort's own spread, which
shrinks its own z-score; the outlier statistically hides itself
("masking"). Leave-one-out removes it at the source: each row's
comparison statistics come from its peers only, never from itself.

## Why Random Forest

Validated against six algorithms on the hospital staffing dataset
(logistic regression, decision tree, random forest, naive bayes, k-NN,
gradient boosting). Random Forest won on every metric that matters for
deployment once its own hyperparameters (particularly `max_features`,
which controls how much randomness each split gets) were tuned
directly, not borrowed from a different model. Full comparison numbers
are in the WGU D797 JCN1 findings log.

## Quick start

```python
from anomaly_toolkit import run_pipeline, build_explainer, explain_row

result = run_pipeline(
    df,
    value_col="the numeric column to screen",
    group_cols=["columns", "that", "define", "a", "peer", "cohort"],
    additional_feature_cols=["other", "context", "columns", "for", "the", "model"],
)

print(result["best_params"])
print(result["threshold_sweep"])

explainer = build_explainer(result["model"], result["X_train"])
row = result["X_test"].iloc[[0]]
for feature, impact in explain_row(explainer, row):
    print(feature, impact)
```

See `examples/run_hospital_staffing.py` for a complete, runnable
reference example against the actual hospital staffing dataset. It is
the pattern to copy when pointing this at a new dataset.

## What `run_pipeline` does

1. Scores `value_col` against its `group_cols` peer cohort with a
   leave-one-out z-score (`scoring.py`).
2. Flags rows past a z-score threshold, using pandas' nullable boolean
   dtype so an unscored row (too few peers) stays missing instead of
   silently becoming `False`.
3. One-hot encodes categorical features, builds a stratified train/test
   split.
4. Runs a randomized hyperparameter search for Random Forest, scored on
   F1 (`classifier.py`).
5. Fits the tuned model and sweeps decision thresholds, since the
   default 0.5 cutoff has no special meaning and the right threshold
   depends on the real cost of a false positive versus a false
   negative for the actual use case.

Explainability (`explain.py`) is separate from the pipeline on purpose,
SHAP is relatively expensive to run, so it's opt-in: call
`build_explainer` and `explain_row` only on the predictions you
actually need to explain.

## Running the tests

```
pip install -r requirements-dev.txt
pytest tests/ -v
```

Runs automatically on every push via GitHub Actions. The tests aren't
generic coverage padding, several of them are regression tests for real
bugs found while building this: the masking effect a plain z-score is
vulnerable to, a pandas gotcha where a missing value silently evaluates
to `False` instead of staying missing, and two SHAP version-compatibility
issues (array shape, dtype casting).

## A known limitation worth keeping in mind

The classifier trains on labels this same pipeline generates (the
peer-cohort flags), not on independently confirmed ground truth. That
is a real limitation, not just a disclaimer: any blind spot in the
scoring step risks being learned and reinforced by the classifier
rather than caught. For a real deployment, replace the pseudo-labels
with confirmed cases (audit outcomes, OIG exclusions, substantiated
investigations) as soon as any exist. `run_pipeline` accepts any binary
label column, the pseudo-labeling in step 1-2 is a default to get
started with, not a requirement.

## What would actually be needed for real Medicare fraud detection

This toolkit is a validated methodology demonstration, not connected to
any real Medicare or CMS data or systems. Getting from here to something
genuinely usable for Medicare program integrity work would need, roughly
in order of how much it would actually move the needle:

1. **Real, confirmed labels.** This is the single biggest gap, bigger
   than any model or feature change. Everything here trains against this
   pipeline's own statistical rule, which caps performance at however
   good that rule is. Real confirmed cases exist publicly: OIG's List of
   Excluded Individuals and Entities (LEIE), settled False Claims Act
   cases, past audit outcomes. Training against those instead of
   pseudo-labels removes the circularity problem entirely rather than
   just managing it.
2. **Linked data, not one table in isolation.** Real fraud analytics
   pulls together claims data (billing codes, amounts, frequency),
   provider enrollment records, ownership and referral networks, patient
   utilization, and license history. This toolkit's peer-group approach
   generalizes to that, the limitation is data access, not the method.
3. **Network analysis for organized fraud.** A lot of real healthcare
   fraud isn't one provider acting strangely, it's shared addresses,
   shared ownership, or referral patterns that don't make clinical
   sense. That's a graph problem (community detection, centrality),
   a different tool family from the row-by-row scoring here.
4. **Change over time, not just difference from peers.** A provider that
   was normal for years and suddenly shifts is one of the strongest real
   signals there is. This toolkit compares a row to its peers at a point
   in time; it doesn't look at trend.
5. **Human-in-the-loop feedback.** Route flagged cases to an
   investigator, record what they actually find, and feed that back into
   retraining. That's active learning, and it solves problem #1
   gradually in a way that doesn't require having confirmed labels
   up front.
6. **Cost-based thresholding.** The threshold sweep here optimizes a
   generic metric (F1). A real deployment would use an actual dollar
   cost matrix (investigator-hour cost per false positive, average
   dollars recovered per confirmed case) and optimize expected net
   value instead.
7. **Drift monitoring.** Fraud patterns adapt once people learn what
   gets flagged. A real system needs ongoing performance monitoring and
   a retraining trigger, not a model trusted indefinitely after one
   training run.

SHAP explainability (already built in) and the leave-one-out peer
scoring (already built in) are two pieces of this list that transfer
directly. The rest is the real distance between a validated
methodology and an operational fraud-detection system.

### Worked example: upcoding

Upcoding, billing a higher-complexity procedure or visit code than what was
actually performed or medically necessary, is one of the most common,
well-documented real Medicare fraud patterns. A frequent form: billing a
high-complexity office visit (CPT 99215) when the visit only warranted a
lower-complexity code (99212-99214). This maps onto the toolkit directly,
and it mirrors how real CMS/OIG program integrity analytics actually work,
comparing a provider's billing pattern against same-specialty peers, not
against providers broadly, since legitimate case complexity varies a lot
by specialty.

- **Value to screen for anomalies**: percentage of a provider's E&M claims
  billed at the highest complexity level.
- **Peer group columns**: specialty, geographic region, facility type. A
  cardiologist's high-level billing rate should be compared against other
  cardiologists in the same region, not against family medicine providers,
  since case complexity legitimately differs by specialty.
- **Extra context columns**: patient volume, payer mix, years in practice,
  anything that provides real context for the classifier without leaking
  the label (see the data-leakage note in `pipeline.py`'s docstring).
- **What a flag means**: a provider whose high-level billing rate is a
  genuine outlier against their own specialty and region, worth a closer
  look, not proof of fraud by itself. OIG has published real audits built
  on exactly this kind of peer-comparison signal.

**This isn't a hypothetical mapping, it's the literal government
definition.** A 2014 OIG report ([OEI-04-10-00181](https://oig.hhs.gov/oei/reports/oei-04-10-00181.asp))
defines a "high-coding physician" as one whose average E&M billing level
sits in the top 1% of their own specialty, billing the two highest-level
codes 95% or more of the time, peer comparison, the same core idea this
toolkit implements. CMS acted on exactly this signal: it issued
"Comparative Billing Reports" to 5,000 physicians nationally who
consistently billed high-level E&M codes, and ran a specific claims audit
targeting code 99215, the same code used in the example above. (Those
sources are from 2012-2014; whether CBRs are still issued in that exact
form today wasn't confirmed.)

This is illustrative, not a ready-to-run example, there's no real claims
dataset wired up here. But it's the concrete shape a real application of
this method would take: same scoring and classification approach, applied
to actual CMS billing data instead of this demonstration's hospital
staffing and animal control datasets.
